# NFC 링크 라이터 — 결정 로그 (최종)

> NFC 제품을 폰으로 인식하면 **조회**(태그에 기록된 링크 목록)와 **수정**(추가·삭제·변경)이 가능한 앱.
> 핵심 UX: URL 패턴이 일정한 포털은 **계정명만 입력하면 전체 URL 자동완성**.

**상태: 45개 결정 확정** (검증 + 3차 정리 + T6 AAR 옵션 반영). 1차 릴리스 범위 = 아래 전부.
**앱 이름: 86400** (2026-09-30 확정) — 미정 항목 없음.

> 🔄 **2차 정리 요약** — 화면은 **홈 + 3페이지**(읽기 · 편집 · 태그 상태 확인),
> 편집 페이지는 **언제나 태그를 읽고 시작**, 앱에는 **아무것도 저장하지 않음**,
> 검사는 **경고 배지만 · 용량 초과만 차단**.
> 이로써 1탭 모드·로컬 캐시·가정 용량이 전부 사라졌습니다.

## STAGE 0 — 전제

| | 내용 |
|---|---|
| ✅ | **NFC 라이터/리더 앱.** 태그에 URL을 직접 굽는 방식 |
| ✅ | **백엔드·서버 없음.** 완전 로컬 구동 |
| ✅ | **수익화 무관.** NFC 사업부 제품에 딸린 앱 |
| ✅ | **차별 축 = UX.** 기존 라이터의 투박함·기능과다·불편함을 푸는 것 |
| ✅ | **태그가 곧 데이터베이스.** 진실의 원천은 태그 안의 NDEF 데이터뿐 |
| ✅ | **용량 제약은 의도된 것.** 링크를 더 넣으려면 태그 추가 구매 |

### 선택 불가한 물리적 제약
1. 읽기는 앱 없이 가능하지만 **쓰기는 네이티브 앱 필수**
   → 앱을 열지 않은 상태에서는 링크로 연결되어야 하므로 **앱이 탭을 가로채면 안 됩니다** (T5)
2. **태그 용량이 링크 개수의 상한**
3. **읽기→편집→쓰기는 태그를 최소 2번 대야 함** — 모든 편집 경로가 그렇습니다
4. **프리셋 패턴이 바뀌면 앱 업데이트 외 대응 불가**

## STAGE 1 — 플랫폼과 물리 제약

| ID | 결정 |
|---|---|
| **P1** | 타깃 플랫폼 = **iOS + Android 둘 다** |
| **P1a** | 구현 방식 = **크로스플랫폼 + NFC 플러그인** |
| **P1b** | 프레임워크 = **React Native** (`react-native-nfc-manager`) |
| **P2** | 태그 칩 = **NTAG213 (144 B)**, 압축 저장 미사용 |
| **P3** | 링크 개수 상한 = **고정값 없음. 태그에서 실제 용량을 읽어 계산** |

> ⚠️ **착수 첫 주 검증 과제:** "빈 태그에 URL 하나 쓰기"만 먼저 관통시킬 것.
>
> **iOS 설정 (검증 완료 — 이대로 하면 됩니다)**
> - Xcode → Signing & Capabilities → **Near Field Communication Tag Reading** 추가
> - 엔타이틀먼트 `com.apple.developer.nfc.readersession.formats` = `NDEF`
> - Info.plist에 **`NFCReaderUsageDescription`** (빈 문자열 불가)
> - 누락 시 세션 시작에서 `NFCReaderErrorSecurityViolation` 발생

### P3. 용량 산정 방식 ✅ **런타임에 태그에서 읽어 계산 — 추정하지 않음**

```
용량   ← 태그가 보고하는 실제 NDEF 메시지 최대 크기
사용량 ← 쓸 NDEF 메시지를 실제로 직렬화해서 바이트 길이 측정
게이지 = 사용량 / 용량        (양쪽 다 실측값, 추정 0)

// react-native-nfc-manager — 크로스플랫폼 단일 API (검증 완료)
NfcManager.ndefHandler.getNdefStatus()
  → { status: NdefStatus, capacity: number }

enum NdefStatus {
  NotSupported = 1,   // NDEF 미포맷 태그
  ReadWrite    = 2,
  ReadOnly     = 3,
}
```

> ✅ **검증 완료 (2026-08-19).** 플랫폼별 분기가 필요 없습니다.
> `getNdefStatus()`가 `NdefHandler` 인터페이스에 **크로스플랫폼으로 선언**되어 있어
> Android `Ndef.getMaxSize()` / iOS `queryNDEFStatus()`를 직접 다룰 일이 없습니다.
> (Android 태그 객체에는 `TagEvent.maxSize?: number`도 별도로 있습니다.)

**이 방식의 이점 3가지**
1. **하드코딩된 144 B·141 B가 사라집니다.** 칩이 NTAG215/216으로 바뀌어도 앱 수정이 불필요합니다.
2. **레코드 오버헤드를 추정할 필요가 없습니다.** 쓸 메시지를 직렬화해 실제 길이를 재면 됩니다.
3. **S1(읽기 전용 태그 감지)이 공짜로 따라옵니다.** 같은 호출이 용량과 상태를 함께 돌려줍니다.
   ⚠️ 단, 상태는 2가지가 아니라 **3가지**입니다 — `NotSupported`(NDEF 미포맷)를 반드시 처리해야 합니다.

> ✅ **가정 용량이 필요 없습니다.**
> U1b에 따라 **편집 페이지는 언제나 태그를 읽고 시작**하므로, 편집을 시작하는 순간
> 이미 실제 용량을 알고 있습니다. 게이지의 분모는 항상 실측값이고
> 추정·재계산·초과 롤백이 전부 불필요합니다.

**참고용 수치 (UI 문구가 아니라 설계 감각용)**
`0x04 = https://` prefix 코드 기준, 레코드 1개 ≈ 5 B + URL 본문.
NTAG213이면 계정명 10자에 5개, 20자면 3개 수준. **UI에는 이 숫자를 노출하지 않습니다.**

## STAGE 2 — 태그 데이터 구조

| ID | 결정 |
|---|---|
| **T1** | 저장 방식 = **다중 URI 레코드 (표준 NDEF)** → 타사 리더 앱에서도 판독됨 |
| **T2** | **앱을 열지 않은 상태**에서 탭하면 = **첫 번째 링크로 연결** (Android는 바로 열림, **iOS는 배너 1번 탭 필요**) |
| **T2a** | 대표 링크 지정 = **하나를 명시적으로 선택.** 선택하면 목록 맨 위로 자동 이동 |
| **T2b** | 저장 시 직렬화 = **대표 링크를 첫 번째 URI 레코드로** 기록 |
| **T3** | 기존 레코드 처리 = **경고 없이 목록에 불러옴** (화면 자체가 설명) |
| **T4** | 태그 UID 식별 = **1차 미포함, 추후 확장** (데이터 구조에 자리만 확보) |
| **T5** | 태그 인텐트 가로채기 = **하지 않음.** `NDEF_DISCOVERED` 인텐트 필터를 등록하지 않음 |
| **T6** | **AAR 레코드 = 지원.** 대표 링크의 프리셋에 연동된 **옵션 1개** |
| **T6a** | AAR은 **태그당 최대 1개.** 대표 링크(T2a)의 프리셋 패키지와 동기화, 대표가 바뀌면 AAR도 따라 바뀜 |
| **T6b** | 직렬화 위치 = **마지막 레코드.** 첫 레코드는 대표 URI(T2b) 유지 |
| **T6c** | 런타임 상태는 **on/off 1개뿐**(현재 대표 기준). 초기값 꺼짐, 켤지는 매번 사용자 판단 — 프리셋별로 따로 저장하지 않음 (대표가 바뀌면 리셋되는 T6i가 이유) |
| **T6d** | 대표가 「기타」면 **옵션 비활성** — 패키지명을 도출할 수 없음 |
| **T6e** | 토글 활성의 전제 = **패키지명 1차 출처 확정.** 6개 전원 확인 완료 |
| **T6f** | 켜는 시점에 **고지 시트** 노출(손해를 먼저 씀). U7 연속 쓰기 중엔 최초 1회만, 수동 재조작 시 다시 노출 |
| **T6g** | iOS에도 노출하되 **"안드로이드에서만 적용"** 명시 |
| **T6h** | **가역** — 태그를 다시 쓰면(U8) AAR도 제거됨 |
| **T6i** | 대표 링크를 바꾸면 AAR 체크박스는 **자동으로 꺼짐** |

### T2 · T2a · T2b. 대표 링크가 작동하는 사슬

```
T1  다중 URI 레코드로 저장
     ↓
    NDEF는 첫 번째 레코드를 연다        ← 물리적 규칙 (선택 불가)
     ↓
T2  앱을 열지 않은 상태에서 탭하면 첫 링크로 연결
      Android — 바로 열림  (T5: 인텐트 필터를 등록하지 않으므로)
      iOS     — 시스템 배너 표시 → 사용자가 배너를 탭해야 열림
     ↓
T2a 그 "첫 링크"를 사용자가 고른다      ← 대표 지정 버튼
     ↓
T2b 저장할 때 대표를 첫 레코드로 직렬화
```

**대표 지정 방식 (수정/만들기 페이지 ②)**

| 동작 | 결과 |
|---|---|
| 항목의 대표 지정 버튼을 누름 | 그 링크가 대표가 되고 **목록 맨 위로 자동 이동** |
| 드래그로 순서 변경 (F5) | 대표를 제외한 나머지 순서를 조정 |
| 대표를 드래그로 아래로 내림 | 대표 지위도 함께 내려가지 않음 — **대표는 명시 선택으로만 바뀜** |

명시적 선택이라 링크가 여러 개여도 맨 위까지 끌어올릴 필요가 없고,
선택하면 맨 위로 올라가므로 **화면 순서와 태그 저장 순서가 항상 일치합니다.**

### T5. "앱을 열지 않은 상태"가 성립하는 조건 (검증 완료)

**설치 여부가 아니라 "우리 앱이 가로채는가"가 관건입니다.**
앱이 설치되어 있어도 태그를 대면 링크로 가야 하는데, Android에서는 앱이 이걸 뺏을 수 있습니다.

| 상황 | 결과 |
|---|---|
| 앱 미설치 | 링크로 연결 ✅ |
| 앱 설치 + **인텐트 필터 미등록** | 링크로 연결 ✅ ← **우리가 택한 것** |
| 앱 설치 + `NDEF_DISCOVERED` 등록 | **우리 앱이 먼저 뜸** ❌ |

**기준은 "앱을 켰는가"가 아니라 "NFC 읽기를 시작했는가"입니다.**

| 상태 | 결과 |
|---|---|
| 앱 미설치 | **대표 URL** |
| 앱 설치 + 미실행 | **대표 URL** |
| 앱 실행 중 + **홈 화면** | **대표 URL** ← U1d로 홈은 태그를 읽지 않음 |
| 앱 실행 중 + **①·②·③의 NFC 대기 상태** | 앱이 읽음 |

앱이 태그를 가져가는 건 **NFC 대기가 켜진 순간부터**입니다.
홈에 머무는 동안은 세션이 없으므로 시스템이 태그를 가져갑니다.

- **Android** — 포그라운드라도 foreground dispatch를 켜지 않으면 시스템 태그 디스패치가 동작합니다.
  T5로 필터를 등록하지 않으므로 `ACTION_VIEW` → 대표 URL.
- **iOS** — Core NFC는 세션을 명시적으로 시작해야만 읽습니다.
  세션이 없으면 배경 리딩이 배너를 띄웁니다.

> 💡 **의도한 동작과 일치합니다.** 사용자가 **편집하러 들어갔을 때만** 앱이 태그를 가져가고,
> 그 외에는 설치·실행 여부와 무관하게 항상 대표 URL입니다.
> 명함처럼 태그를 내밀 때 **내 폰에 앱이 깔려 있든 말든 상대에겐 똑같이 동작합니다.**

**Android**
`ACTION_NDEF_DISCOVERED`는 **최우선 인텐트**입니다. 이 필터를 등록한 앱이 있으면
시스템이 브라우저보다 먼저 그 앱을 띄웁니다. 따라서 **등록하지 않는 것이 요구사항입니다.**

> 📌 **Android 16부터는 등록해도 못 가로챕니다.**
> URI 스킴이 `http://`·`https://`인 웹 링크 태그는 `NDEF_DISCOVERED`가 아니라
> **`ACTION_VIEW`를 트리거**하도록 바뀌었습니다. 우리 태그는 전부 https URI 레코드이므로
> Android 16+에서는 자동으로 링크로 갑니다. 그 이하 버전을 위해 T5를 지켜야 합니다.

**iOS**
가로챌 방법이 애초에 없습니다. 배경 태그 리딩에서 앱으로 전달되려면 **Universal Link**여야 하는데,
서버·도메인이 없는 이 제품은 Universal Link를 만들 수 없습니다 → **항상 배너 → Safari**입니다.

> 💡 **링크 대상 서비스의 앱은 열려도 됩니다.**
> 인스타그램 앱이 깔려 있으면 `instagram.com/...` 링크가 인스타그램 앱으로 열립니다
> (iOS Universal Links / Android App Links). 이건 우리 앱과 무관하며 **바람직한 동작**입니다.
> 사용자는 브라우저가 아니라 인스타그램 앱에서 프로필을 보게 됩니다.

> ⚠️ **iOS에서 배경 읽기가 아예 안 되는 조건이 있습니다.**
> 기기가 한 번도 잠금 해제되지 않음 · Core NFC 세션 진행 중 · Apple Pay 지갑 사용 중 ·
> 카메라 사용 중 · 비행기 모드. 이때는 배너조차 뜨지 않습니다.

> ⚠️ **iOS는 완전 자동이 아닙니다 (검증 완료).**
> iOS 13+ 백그라운드 태그 리딩은 **시스템 배너를 띄우고 사용자가 배너를 탭해야** URL이 열립니다.
> 애플이 의도한 프라이버시·보안 설계이며 우회할 수 없습니다 (iPhone XS 이후 지원).
> Android는 바로 열립니다.
> → **"태그만 대면 바로 연결된다"는 문구를 제품 설명에 쓰면 iOS에서 어긋납니다.**
> 대표 링크의 가치는 그대로입니다 — 배너에 뜨는 것도 첫 레코드이기 때문입니다.

**필수 UI 요구사항**
사용자는 "왜 대표가 중요한지" 모릅니다. 대표 항목에 **"탭하면 이 링크가 열립니다"** 배지를 상시 노출하고, 대표를 바꾸면 배지가 따라 움직이는 게 보여야 개념이 학습됩니다. 대표 지정은 정렬이 아니라 **앱 없는 사람이 볼 화면을 정하는 행위**입니다.

> 📌 **대표는 항상 정확히 1개입니다.** 링크가 1개뿐이면 자동으로 대표이고,
> 대표를 삭제하면 그다음 항목이 자동으로 대표가 됩니다. "대표 없음" 상태는 존재하지 않습니다.

> 🗑 **"태그 복제"는 1차 범위에서 빠집니다.**
> 이전에는 U7의 두 번째 갈래(②에 머무름)가 복제 통로 역할을 했지만,
> U7이 **같은 태그에 이어서 추가하는 흐름**으로 바뀌면서 그 통로가 사라졌습니다.
> U2(앱 저장 없음) 때문에 링크 세트를 다른 태그로 옮길 방법이 남아 있지 않습니다.
>
> 빈 태그 여러 개에 같은 세트를 쓰려면 **태그마다 처음부터 다시 입력**해야 합니다.
> 필요해지면 T4(태그 UID 식별)와 함께 추후 확장에서 다루는 게 맞습니다.

### T6~T6i. AAR(Android Application Record) — 옵션 (검토 완료)

**배경.** 대학생 네트워킹 실사용에서, 구형 안드로이드가 인스타그램 대표 링크를 브라우저 경유로
열어 불편감과 낮은 신뢰도가 관측되었습니다. AAR을 함께 기록하면 안드로이드에서 브라우저를
거치지 않고 해당 앱이 바로 열립니다. 단, **앱이 없는 기기에서는 링크 대신 Google Play가 열립니다**
— 이 손해는 되돌릴 수 없고(태그는 물리 매체), 그 손해를 보는 사람은 태그를 만든 사람이 아니라
**태그를 받는 상대방**입니다. 그래서 판단과 고지 책임을 사용자에게 넘기는 형태로 설계했습니다
(전체 검토: `PREMORTEM-AAR.md`, 사양: `SPEC-T6-AAR.md`).

**프리셋 6종 패키지명과 초기값**

| 프리셋 | 패키지명 | 초기값 |
|---|---|---|
| Instagram | `com.instagram.android` | 꺼짐 |
| GitHub | `com.github.android` | 꺼짐 |
| LinkedIn | `com.linkedin.android` | 꺼짐 |
| X | `com.twitter.android` | 꺼짐 |
| TikTok | `com.zhiliaoapp.musically` | 꺼짐 |
| YouTube | `com.google.android.youtube` | 꺼짐 |
| 기타 | — | 토글 없음 (T6d) |

**화면.** 링크 목록 맨 위, 어떤 링크 행에도 붙지 않는 **고정 패널**에 `현재 대표: OO` + 체크박스
하나만 있습니다. 대표는 항상 목록 1번 자리로 이동하므로(T2a) 패널이 자연히 그 대표를 따라갑니다.
켜는 순간 *"앱이 없으면 링크 대신 앱 설치 화면이 열립니다"* 를 먼저 보여주는 고지 시트가 뜨고,
기본 포커스는 「켜지 않음」입니다. ① 읽기 화면과 ③ 진단 화면 모두 AAR이 있으면 상태를 표시합니다.

> 💡 **U5(태그 잠금)와 다른 점.** lock bit은 비가역이라 노출하지 않기로 했습니다(U5).
> AAR은 태그를 다시 쓰면 해제되는 **가역** 설정이라 같은 처리를 하지 않고 노출합니다(T6h).

## STAGE 3 — 기능 정의

| ID | 결정 |
|---|---|
| **F1** | 프리셋 범위 = **글로벌 서비스 우선**, 국내 서비스는 1차 제외 |
| **F1a** | 1차 프리셋 = **6개 + 기타 1개** |
| **F2** | 입력 정규화 = **선택(프리셋/기타)이 먼저, 그다음 두 갈래 분기** |
| **F2a** | 대소문자 = **입력 그대로 보존** |
| **F2b** | 같은 서비스 중복 추가 = **허용하되 경고** |
| **F3** | 커스텀 URL 직접 입력 = **지원.** 프리셋의 "기타" 선택지 1개로 통합, **어떤 URL이든 허용**, **저장 개수 무제한** (용량만이 제한) |
| **F4** | 프리셋 갱신 = **앱 업데이트로만.** 사용자 직접 패턴 등록은 없음 |
| **F5** | 링크 순서 변경 = **필수** (드래그 정렬. 대표 지정은 T2a의 명시 선택으로 별도) |
| **F6** | 수정 범위 = **조회 · 추가 · 삭제 · 기존 링크 수정 전부** |
| **F7** | 프리셋 선택 UI = **세로 리스트** (이름 + 설명. 프리셋 확대를 전제) |

### F1a. 프리셋 목록과 레코드 크기

| 서비스 | 패턴 | 크기 | 핸들 10자 | AAR 초기값 |
|---|---|---|---|---|
| X | `x.com/{handle}` | 11 + H | 21 B | 꺼짐 |
| GitHub | `github.com/{handle}` | 16 + H | 26 B | 꺼짐 |
| TikTok | `tiktok.com/@{handle}` | 17 + H | 27 B | 꺼짐 |
| YouTube | `youtube.com/@{handle}` | 18 + H | 28 B | 꺼짐 |
| Instagram | `instagram.com/{handle}` | 19 + H | 29 B | 꺼짐 |
| LinkedIn | `linkedin.com/in/{handle}` | 21 + H | 31 B | 꺼짐 |
| **기타** | 사용자가 URL 직접 입력 | 5 + 전체 URL | 가변 (60~80 B도 발생) | 토글 없음 |

> **AAR 초기값 열 — T6 (STAGE 2).** 6개 전부 꺼짐에서 시작, 사용자가 켤지 정합니다.
> 켜면 프리셋별 패키지명(T6~T6i 절 참고)으로 AAR 레코드 40 B가 추가로 소모됩니다.

> ⚠️ **프리셋은 7개지만 태그엔 다 안 들어갑니다.**
> NTAG213 기준 6개 전부는 초과하고 가벼운 5개만 겨우 들어갑니다.
> **"선택지 개수 ≠ 저장 가능 개수"** — 이건 P3의 실측 게이지가 대신 설명합니다.
> 위 표의 바이트 값은 **설계 감각용 참고치이며 UI에 노출하지 않습니다.**

> 📌 **"기타"는 프리셋 목록의 선택지 1개이고, 저장 개수에는 제한이 없습니다.**
> 커스텀 URL을 2개, 3개 넣어도 됩니다. **유일한 제한은 용량**이고 U4 게이지가 그 역할을 합니다.
>
> 파생 규칙 2가지:
> - **중복 경고(F2b) 적용 범위** — 프리셋 서비스는 *같은 서비스*가 겹칠 때 경고,
>   기타는 서비스 개념이 없으므로 **URL이 완전히 동일할 때만** 경고
> - **목록 표시** — 기타가 여러 개면 전부 "기타"로 보여 구분이 안 됩니다.
>   URL에서 **도메인을 뽑아 라벨로 표시**해야 합니다 (예: `notion.so`, `velog.io`)

### F2. 입력 정규화 파이프라인 — **선택이 먼저, 그다음 두 갈래**

```
                    ┌──────────────────────────┐
             0단계  │  프리셋 도메인 / 기타 선택  │  ← 이 선택이 이후 전부를 가른다
                    └───────────┬──────────────┘
                    ┌───────────┴──────────────┐
                    ▼                          ▼
            [프리셋 분기]                   [기타 분기]
          입력 = 계정명 (URL 아님)          입력 = URL 전체
```

**프리셋 분기 — 계정명만 받아 URL을 조립**

```
P1. 앞뒤 공백 제거
P2. 전체 URL 붙여넣기 감지
      선택한 프리셋 도메인과 일치 → 계정명만 추출
      다른 도메인                → "기타로 추가할까요?" 제안
P3. 선행 @ 제거              (유튜브·틱톡은 저장 시 다시 붙임 = 입력과 저장을 분리)
P4. 끝의 / 제거
P5. 허용 문자 검증            영숫자 . _ - 만 / 한글·공백·슬래시는 경고
P6. 대소문자 그대로 보존       (F2a)
P7. URL 조립  ★              프리셋 패턴 + 계정명 → 완성된 URL
                             예) Instagram + "hong" → https://instagram.com/hong
P8. 중복 감지                같은 서비스가 이미 있으면 경고 배지
```

**기타 분기 — 어떤 URL이든 그대로 받음**

```
E1. 앞뒤 공백 제거
E2. 스킴 없으면 https:// 자동 부착
E3. URL 형식 검증만           슬래시 · 쿼리스트링 · 포트 · 경로 전부 허용
E4. 도메인 추출              목록에서 라벨로 사용 (예: notion.so, velog.io)
E5. 중복 감지                URL이 완전히 같을 때만 경고 배지
```

> ⚠️ **P5는 프리셋 분기에만 적용됩니다.**
> 슬래시·콜론 차단을 공통 단계로 두면 기타의 정상적인 URL이 전부 걸립니다.
> "기타는 어떤 URL이든 삽입 가능"이 성립하려면 두 분기가 **분리되어 있어야** 합니다.

> 📌 **모든 검사는 경고 배지이고 저장을 막지 않습니다** (U4c).
> P5의 허용 문자 위반도, E3의 형식 이상도 경고까지입니다.
> 앱이 물리적으로 막을 수 있는 건 **용량 초과뿐**입니다.

**계정 실존 여부는 검증 불가** (서버가 없으므로). 형식 검증만 가능합니다.

## STAGE 4 — 화면 구조와 탭 인터랙션

| ID | 결정 |
|---|---|
| **U1** | 화면 구조 = **홈 + 3페이지** (읽기 · 수정/만들기 · 태그 상태 확인) |
| **U1b** | 편집 페이지 진입 = **언제나 태그를 읽고 시작** (신규·수정 구분 없음) |
| **U1c** | 저장 = **버튼을 누르면 즉시 NFC 대기** (별도 안내 단계 없음) |
| **U1d** | 홈 = **3갈래 진입점만.** 홈에서는 태그를 읽지 않음 |
| **U1e** | 태그 상태 확인 = **읽기 전용 진단 페이지.** 상태를 보여주기만 하고 쓰지 않음 |
| **U2** | 로컬 저장 = **없음.** 앱은 아무것도 남기지 않음 (태그가 유일한 저장소) |
| **U3** | 쓰기 실패 처리 = **쓰기 후 검증 재읽기** |
| **U4** | 용량 표시 = **입력 단계에서 실시간 표시** (분모는 태그가 보고한 실제 용량) |
| **U4a** | 용량 초과 안내 = **단순 경고만** (판매 유도 문구 없음) |
| **U4b** | 표기 단위 = **게이지 바 + 바이트 수치 병기** (예: `87 / 137 B`) |
| **U4c** | 검사 차단 정책 = **경고 배지만. 용량 초과만 저장 차단** |
| **U5** | 태그 잠금(lock) = **노출 안 함** (lock bit는 비가역 — 검증 완료) |
| **U6** | ①에서 링크 탭 = **탭하면 브라우저로 열기, 길게 누르면 URL 복사** |
| **U7** | 저장 성공 후 = **완료 화면 표시 후 사용자가 선택** (완료 → 홈 / 링크 더 추가하기 → **프리셋 선택 페이지 직행**) |
| **U8** | 쓰기 실패 처리 = **전체 재쓰기 유도** (부분 기록 가능성 때문) |
| **U9** | iOS 세션 타임아웃 = **다시 시도 버튼 표시.** 자동 재시작 안 함 |
| **U10** | 홈 레이아웃 = **같은 크기 버튼 3개 세로 배치** + 각 한 줄 설명 |
| **U11** | ③에서 ②로의 유도 = **없음.** ③은 진단만 하고 나갈 때는 홈으로 |

### U1 · U1d. 홈과 3페이지

```
                        ┌─────────────┐
                        │     홈      │  ← 태그를 읽지 않음. 갈래만 고름
                        └──────┬──────┘
             ┌─────────────────┼─────────────────┐
             ▼                 ▼                 ▼
      ① 읽기 페이지     ② 수정/만들기      ③ 태그 상태 확인
      탭 1회            탭 2회             탭 1회
      링크 목록 조회     읽기→편집→저장      용량·쓰기가능·포맷 진단
             │
             └──[수정]──▶ ②로 이동 (읽은 데이터 전달, 재읽기 없음)
```

| 페이지 | 태그 접촉 | 하는 일 | 쓰기 |
|---|---|---|---|
| ① 읽기 | 1회 | 태그의 링크 목록 조회 | ✗ |
| ② 수정/만들기 | 2회 (읽기 1 + 저장 1) | 추가·삭제·수정 · **대표 지정(T2a)** · 순서 변경(F5) 후 태그에 기록 | ✓ |
| ③ 태그 상태 확인 | 1회 | 태그 자체의 상태 진단 (막다른 페이지 — U11) | ✗ |

**①과 ③은 태그를 건드리지 않는 읽기 전용 페이지입니다.** 쓰기가 일어나는 곳은 ②뿐입니다.

**U1b가 해결하는 것:** ②는 편집 시작 시점에 실제 용량을 이미 알고 있으므로
가정 용량·재계산·초과 롤백이 전부 사라집니다 (P3 참조).
빈 태그를 읽으면 목록이 비어 있을 뿐이므로 **"만들기"와 "수정"이 별도 모드로 존재하지 않습니다.**

### U1e. 태그 상태 확인 페이지가 보여주는 것

P3의 런타임 용량 조회가 돌려주는 값을 그대로 화면에 펼친 것입니다. 별도 구현이 거의 없습니다.

| 항목 | 출처 |
|---|---|
| 전체 용량 / 사용량 / 남은 용량 | `getNdefStatus().capacity` + 현재 메시지 직렬화 |
| 쓰기 가능 여부 | `getNdefStatus().status` |
| NDEF 포맷 여부 | `status === NotSupported` |
| 기록된 레코드 개수 | 읽은 NDEF 메시지 |

**상태 3가지를 전부 화면에 정의해야 합니다** (검증에서 드러난 항목):

| `NdefStatus` | 화면 | ②에서 할 수 있는 것 |
|---|---|---|
| `ReadWrite` (2) | 정상 — 용량 게이지 표시 | 전부 가능 |
| `ReadOnly` (3) | "이 태그는 잠겨 있습니다" | 조회만. 저장 차단 |
| `NotSupported` (1) | "NDEF 태그가 아닙니다" | **포맷 유도 또는 사용 불가 안내** |

> ⚠️ **U5와 충돌하지 않습니다.** 이 페이지는 잠금 상태를 **표시만** 합니다.
> 잠금을 *실행하는* 기능은 여전히 없습니다 (lock bit는 비가역이므로).

> 💡 **S1이 이 페이지로 흡수됩니다.** "읽기 전용·손상 태그를 어떻게 안내할 것인가"가
> ①·②에 흩어진 예외 처리가 아니라 **전용 페이지 하나**로 정리됩니다.
> ①·②에서 이상이 감지되면 ③으로 유도합니다.
> **단, 방향은 한쪽뿐입니다** — ③에서 ②로 돌아가는 버튼은 두지 않습니다 (U11).

### U4c. 무엇을 막고 무엇을 막지 않는가

| 상황 | 처리 |
|---|---|
| 같은 서비스 중복 | 경고 배지, **저장 가능** |
| 커스텀 URL 완전 중복 | 경고 배지, **저장 가능** |
| 형식 오류 (허용 문자 위반 등) | 경고 배지, **저장 가능** |
| **용량 초과** | **저장 차단** — 물리적으로 쓸 수 없으므로 |

경고는 배지로만 표시하고 다이얼로그를 띄우지 않습니다. 판단은 사용자가 합니다.

```
[완료 화면]  "저장했습니다"
   ├─ 완료             → 홈으로
   └─ 링크 더 추가하기  → 프리셋 선택 페이지로 직행 (홈을 거치지 않음)
                          같은 태그에 링크를 이어서 추가
```

**같은 태그에 연속으로 등록하는 흐름입니다.** 방금 쓴 태그의 용량과 내용을
이미 알고 있으므로 **태그를 다시 읽지 않고** 프리셋 선택으로 바로 갑니다.

| | 이어지는 것 |
|---|---|
| 태그 용량 | 방금 읽은 실측값 그대로 (재읽기 불필요) |
| 현재 링크 목록 | 방금 저장한 내용 그대로 유지 |
| 용량 게이지 | 이어서 갱신 — 추가할수록 채워짐 |
| 대표 링크 | 기존 대표 유지 (T2a로 바꿀 수 있음) |

> ✅ **U1b와 충돌하지 않습니다.** "편집은 언제나 태그를 읽고 시작"인데,
> 이 경로는 **이미 읽은 상태의 연장**이지 새로운 시작이 아닙니다.
> 가정 용량이 끼어들 여지가 없습니다.

> ⚠️ **저장은 매번 탭이 필요합니다.** 링크를 추가한 뒤 다시 저장을 누르면
> 태그를 한 번 더 대야 합니다 (U1c). 추가할 때마다 쓰기가 일어납니다.

> 📌 **용량이 차면 U4c가 막습니다.** 계속 추가하다 용량을 넘기면
> 저장 버튼이 차단되고 무엇을 빼야 하는지 보여줍니다.

**U8 — 쓰기 실패**
NDEF 쓰기는 중간에 끊기면 **부분 기록이 남을 수 있습니다.**
U3의 검증 재읽기가 불일치를 잡아내면 재시도가 아니라 **처음부터 전체를 다시 씁니다.**
이미 깨진 태그에 같은 쓰기를 반복하면 실패가 반복되기 때문입니다.

**U9 — iOS 세션 타임아웃**
자동으로 세션을 다시 열지 않고 **"다시 시도" 버튼**을 보여줍니다.
사용자가 준비됐을 때 누르므로 동작이 예측 가능하고,
그만두려는 사람에게 NFC 대기가 계속 열리는 일이 없습니다.

### U11. ③은 막다른 진단 페이지

들어오는 길은 있고 나가는 길은 홈뿐입니다.

```
①·②에서 이상 감지  ──▶  ③ 태그 상태 확인  ──▶  홈
                          (진단만. 수정 버튼 없음)
```

③에 수정 버튼을 두지 않으므로 **쓰기가 일어나는 곳은 ②뿐**이라는 원칙이 흐트러지지 않습니다.
사용자는 상태를 확인한 뒤 홈에서 ②를 다시 고릅니다.

**U3의 의미:** 쓴 직후 같은 세션에서 다시 읽어 일치를 확인합니다.
→ 사용자에게 "저장됨"이라고 말하는 시점이 **실제로 검증된 시점**이 됩니다.
→ 태그를 대고 있어야 하는 시간이 늘어나므로 진행 표시가 정확해야 합니다.

### 검증에서 문서와 달랐던 것 2가지

**① iOS는 자동으로 열리지 않습니다** 🔴 *(T2 수정 완료)*
iOS 13+ 백그라운드 태그 리딩은 **시스템 배너를 띄우고 사용자가 탭해야** 열립니다.
"자동으로 열림"은 Android 기준이었습니다. 우회 불가 — 애플의 의도된 설계입니다.

**② 상태가 2가지가 아니라 3가지입니다** *(U1e·S1 수정 완료)*
`NdefStatus.NotSupported`(NDEF 미포맷)를 빠뜨리고 read-only / read-write만 가정했습니다.

### 프리셋 표기 조정 2건

| 서비스 | 문서 표기 | 실제 표준 표기 |
|---|---|---|
| Instagram | `instagram.com/{handle}` | `www.instagram.com/{handle}/` (www + 끝 슬래시) |
| TikTok | `tiktok.com/@{handle}` | `www.tiktok.com/@{handle}` (www) |

> 📌 **기능 영향 없음.** NDEF 프리픽스 `0x02 = https://www.`가 www를 1바이트로 압축하고,
> 용량은 P3 실측이므로 바이트 표의 오차는 게이지에 영향을 주지 않습니다.
> 다만 **자동완성이 만들 URL 문자열은 실제 표준 표기를 따르는 게 안전**합니다.

> ✅ **YouTube 핸들 규칙이 P5와 정확히 일치합니다.** 3~30자, 영숫자 · `.` `_` `-`.
> P5의 허용 문자셋을 그대로 쓰면 됩니다.
