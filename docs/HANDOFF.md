## 0. 제품 한 줄 정의

NFC 태그에 URL을 직접 굽는 **로컬 전용** 라이터/리더 앱. 서버·백엔드·로그인·로컬 저장 **없음**.
진실의 원천은 **태그 안의 NDEF 데이터뿐**입니다. 핵심 UX는 URL 패턴이 일정한 서비스(Instagram,
GitHub 등)를 고르면 **계정명만 입력**해 전체 URL을 자동완성하는 것입니다.

### 넘을 수 없는 물리 제약 (설계 전제)

1. 읽기는 앱 없이 가능 · **쓰기는 네이티브 앱 필수** → 앱을 안 열었을 때는 태그가 링크로
   연결돼야 하므로 **앱이 탭을 가로채면 안 됨**
2. 태그 용량이 저장 가능한 링크 개수의 물리적 상한
3. 읽기→편집→쓰기는 **태그를 최소 2번** 대야 함
4. 프리셋 URL 패턴이 바뀌면 앱 업데이트로만 대응 가능 (서버로 원격 갱신 불가)

## 1. 기술 스택

| 항목 | 값 |
|---|---|
| 플랫폼 | iOS + Android 둘 다 |
| 프레임워크 | **React Native** |
| NFC 라이브러리 | **`react-native-nfc-manager`** |
| 태그 칩 (기준) | NTAG213 (144 B) — 코드에 하드코딩하지 않음, 런타임에 실측 |
| 서버/백엔드 | 없음 |
| 로컬 저장 (AsyncStorage 등) | **없음.** 앱은 아무것도 남기지 않음 |

### iOS 설정 (검증 완료 — 그대로 적용)

1. Xcode → Signing & Capabilities → **Near Field Communication Tag Reading** 추가
2. 엔타이틀먼트 `com.apple.developer.nfc.readersession.formats` = `NDEF`
3. `Info.plist`에 **`NFCReaderUsageDescription`** 문자열 (빈 문자열 불가)
4. 누락 시 `readerSession:didInvalidateWithError:`로 `NFCReaderErrorSecurityViolation` 발생

### 라이브러리 핵심 API (타입 정의 확인 완료)

```typescript
interface NdefHandler {
  writeNdefMessage: (bytes: number[], options?: { reconnectAfterWrite: boolean }) => Promise<void>;
  getNdefMessage: () => Promise<TagEvent | null>;
  makeReadOnly: () => Promise<void>;               // 사용하지 않음 — §6 참고
  getNdefStatus: () => Promise<{ status: NdefStatus; capacity: number }>;
  getCachedNdefMessageAndroid: () => Promise<TagEvent | null>;
}

enum NdefStatus {
  NotSupported = 1,   // NDEF로 포맷되지 않은 태그
  ReadWrite    = 2,   // 정상
  ReadOnly     = 3,   // 잠김
}
```

`getNdefStatus()`는 **크로스플랫폼 단일 호출**입니다. Android용 `Ndef.getMaxSize()`,
iOS용 `queryNDEFStatus()`를 따로 부를 필요가 없습니다. (Android 태그 객체에는
`TagEvent.maxSize?: number`가 별도 존재하지만 쓸 필요 없음.)

### ⚠️ 착수 1주차 스파이크 — 가장 먼저 검증할 것

**"빈 태그에 URL 하나 쓰기"** 한 가지만 먼저 관통시키세요. 아래 3개 값이 이 스파이크에서
실측되어야 합니다 (문서로는 확인 불가, §7 참고):

- `getNdefStatus()`가 **NTAG213 실물**에서 반환하는 `capacity` 값
- iOS 세션 타임아웃 실제 시간 (통설 60초, 미확인)
- `writeNdefMessage`의 `reconnectAfterWrite` 옵션이 §5.7 검증 재읽기에 그대로 쓰이는지

## 2. 데이터 모델 — 태그 안에 무엇이 어떻게 들어가는가

### 2.1 기본 구조 — 다중 URI 레코드

- 저장 방식 = **표준 NDEF, 다중 URI 레코드**. 타사 NFC 리더 앱에서도 판독 가능해야 함.
- **대표 링크**(사용자가 명시적으로 지정한 링크 1개)를 **첫 번째 레코드**로 직렬화.
  → iOS·Android 모두 다중 레코드 중 **첫 번째 유효 레코드만 해석**하므로, 앱 없이 태그를
  대면 대표 링크로 연결됩니다.
- 기존에 다른 앱이 써둔 레코드가 있어도 **경고 없이 그대로 목록에 불러옵니다** — 삭제하지 않음.
- 대표 지정은 **드래그 정렬과 무관**합니다. 명시적으로 "대표로 지정" 액션을 눌러야만 바뀌고,
  누르면 그 링크가 목록 1번 자리로 자동 이동합니다. 대표는 항상 정확히 1개 —
  링크가 1개면 자동 대표, 대표를 삭제하면 다음 항목이 자동 승계.

### 2.2 용량 계산 — 추정하지 않고 항상 실측

```
용량   ← getNdefStatus().capacity          (태그가 보고하는 실제 값)
사용량 ← 쓸 NDEF 메시지를 실제로 직렬화한 바이트 길이
게이지 = 사용량 / 용량                      (양쪽 다 실측, 추정 0)
```

편집 화면은 **항상 태그를 먼저 읽고 시작**하므로(§5.3), 편집을 시작하는 순간 이미 실제
용량을 알고 있습니다. 가정 용량·재계산·초과 롤백 로직은 만들 필요가 없습니다.

참고용 감각치(코드에 하드코딩하지 말 것 — UI에도 노출 안 함): `0x04 = https://` 프리픽스
기준 레코드 1개 ≈ 5 B + URL 본문. NTAG213(144B)이면 계정명 10자 기준 링크 5개 정도.

### 2.3 AAR (Android Application Record) — 옵션 기능

대표 링크의 프리셋에 앱이 있으면(Instagram 등), 안드로이드 구형 기기에서 브라우저를
거치지 않고 해당 앱을 바로 열게 하는 **선택적** NDEF 레코드입니다. `NdefRecord.createApplicationRecord(packageName)`,
TNF_EXTERNAL_TYPE `android.com:pkg`.

**동작 규칙 (Android 공식 문서 기준)**

1. 인텐트 필터로 먼저 액티비티를 찾고, 그 액티비티가 AAR과도 일치하면 그걸 실행
2. 불일치/후보 여럿/처리 앱 없음 → **AAR이 지정한 앱을 실행**
3. **그 앱이 없으면 → Google Play가 열림** (이게 이 옵션의 유일한 손해 지점)
4. AAR은 **메시지 전체**에서 탐색되지만 **첫 레코드로 쓰면 안 됨** (AAR이 유일한 레코드인
   경우 제외) — 시스템이 첫 레코드로 MIME/URI를 판별하기 때문

**저장 규칙**

**2026-10-11 사용자 정정:** 기존 태그에서 읽은 AAR은 원본 필드와 바이트를 보존한다. 링크 수정·삭제·대표 변경으로 자동 제거하지 않으며, 편집 화면에서 기존 앱 설정과 켜짐 상태를 표시한다. 사용자가 직접 끄면 제거하고, 「대표 앱으로 변경」에서 고지를 승인하면 기존 AAR을 선택한 대표 앱의 AAR 1개로 교체한다. 아래 초기값 꺼짐·대표 변경 시 꺼짐 규칙은 새로 선택하는 AAR에 적용한다. 이미 여러 AAR이 있는 외부 태그도 임의 삭제하지 않으며 신규/교체 시에는 최대 1개만 쓴다. iOS에서 AAR 보존 쓰기는 실측 전까지 차단한다.

| 규칙 | 내용 |
|---|---|
| 개수 | 태그당 **최대 1개**. 대표 링크의 프리셋과 항상 동기화 |
| 직렬화 위치 | **마지막 레코드**. 첫 레코드는 대표 URI 그대로 유지 (§2.1) |
| 갱신 방식 | 전체 재쓰기에서도 **기존 AAR은 유지**. 사용자가 끄거나 교체할 때만 제거·변경 |
| 런타임 상태 | **on/off 1개뿐**(현재 대표 기준). `Record<프리셋, boolean>`처럼 6개를 따로 저장하지 않음 |
| 초기값 | **꺼짐.** 사용자가 매번 켤지 판단 — 대표가 바뀌면 자동으로 다시 꺼짐(아래 "대표 변경 시" 행)이므로 프리셋별로 이전 선택이 기억되지 않음 |
| 대표 변경 시 | 대표를 바꾸면 AAR 체크박스는 **자동으로 꺼짐** (다른 서비스로 새로 켜야 함) |
| 「기타」 대표 | AAR 옵션 **비활성** — 패키지명을 도출할 수 없음 |
| iOS | 스위치는 노출하되 **"안드로이드에서만 적용됨"** 문구 명시 |
| 가역성 | 사용자가 앱 바로 열기 설정을 끄고 저장하면 AAR 제거 — lock bit와 달리 **되돌릴 수 있음** |

## 3. 화면 구조

```
                    ┌──────┐
                    │  홈  │  ← 태그를 읽지 않음. 갈래만 고름
                    └──┬───┘
        ┌──────────────┼──────────────┐
        ▼               ▼              ▼
   ① 읽기          ② 수정/만들기      ③ 태그 상태 확인
   탭 1회           탭 2회             탭 1회
   조회 전용         읽기→편집→쓰기      진단 전용 (막다른 페이지)
```

| 페이지 | 태그 접촉 | 쓰기 | 하는 일 |
|---|---|---|---|
| ① 읽기 | 1회 | ✗ | 태그의 링크 목록 조회 |
| ② 수정/만들기 | 2회 (읽기 1 + 저장 1) | ✓ | 추가·삭제·수정·대표 지정·순서 변경 후 기록. **쓰기가 일어나는 유일한 페이지** |
| ③ 태그 상태 확인 | 1회 | ✗ | 태그 자체 상태 진단. 나가는 길은 홈뿐 |

- **①·③은 읽기 전용.** 쓰기는 ②에서만 일어납니다.
- **②는 신규/수정 모드 구분이 없습니다.** 빈 태그를 읽으면 목록이 비어 있을 뿐 — "만들기"가
  별도로 존재하지 않습니다. 항상 태그를 읽고 시작.
- **①에서 "수정하기"를 누르면 ②로 이동하되 태그를 다시 읽지 않습니다** (①에서 읽은 데이터를
  그대로 넘김).
- ①·②에서 읽기 전용/손상 태그가 감지되면 ③으로 유도. **③에서 ②로 돌아가는 버튼은 없음**
  (한 방향 동선 — "쓰기는 ②에서만"이라는 원칙 유지).

## 4. 화면별 사양

### 4.1 홈

**목적.** 무엇을 할지 먼저 고르는 화면. 세 갈래가 태그 접촉 횟수가 다르므로 선택이 태그
접촉보다 먼저입니다. **여기서는 NFC 세션을 열지 않습니다** (요구사항 — 열면 명함처럼 태그를
내밀 때 상대 폰이 아니라 이 앱이 태그를 가져가 버림).

| # | 요소 | 설명 |
|---|---|---|
| 1 | 상단 바 | 앱 이름 **86400** (2026-09-30 확정) |
| 2 | 갈래 버튼 3개 | 같은 크기, 세로 배치, 각 한 줄 설명. 특정 기능을 앞세우지 않음 |
| 3 | 버튼 문구 (고정) | **링크 보기 / 링크 편집 / 태그 상태 확인** |

**없는 것:** 태그 읽기, 최근 태그·저장된 링크 목록(로컬 저장 없음), 로그인/계정.

---

### 4.2 ① 읽기

**목적.** 태그에 담긴 링크를 확인만. 태그 접촉 1회, 쓰기 없음.

**진입·재시도 (2026-10-09 사용자 변경·Android 확인).** 홈에서 "링크 보기"를 선택하면
① 화면에 처음 진입할 때 자동으로 읽기 대기를 시작합니다. "태그 읽기" 버튼을 먼저 누를 필요가 없습니다.
홈은 화면 이동만 수행하며 NFC 세션은 ①에서 시작합니다. 읽기 대기 중 화면을 나가면 진행 요청을 취소합니다.
읽은 뒤 편집 화면이나 링크를 연 외부 앱에서 기존 ①로 돌아오면 결과를 유지하며 자동으로 다시 읽지 않습니다.
홈에서 새로 ①에 진입하면 다시 자동 읽기를 시작합니다. 실패·취소 후에는 자동 재시도하지 않고 사용자가
"태그 읽기"로 재시도하며, 읽기 성공 후 다른 태그를 읽을 때는 "다시 읽기"를 누릅니다.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 상단 바 | 뒤로(홈) + 읽기 완료 표시 |
| 2 | 링크 목록 | 태그에 기록된 순서 그대로 (첫 항목 = 대표) |
| 3 | 대표 배지 | **"탭하면 이 링크가 열립니다"** 상시 노출 — 대표 개념을 학습시키는 핵심 UI |
| 3a | 읽기 전용 AAR 카드 | URI 목록·열기/복사 안내 뒤에 실제 저장된 AAR별 **"앱 바로 열기 레코드 / 서비스명 / 태그에 저장됨"** 표시. 미등록 패키지는 원문, 손상/빈 패키지는 "패키지 확인 불가". AAR 없으면 카드 없음. 링크 열기·복사 없음. 전체 용량에 중복 합산하거나 URI 개수에 포함하지 않음 (**2026-10-09 사용자 변경·확인**) |
| 4 | 기타 링크 라벨 | 프리셋이 아니면 서비스 개념이 없으므로 **URL에서 도메인을 뽑아** 표시 |
| 5 | 항목 인터랙션 | 탭 = 브라우저로 열기, 길게 누르기 = URL 클립보드 복사 |
| 6 | "수정하기" 버튼 | ②로 이동. **읽은 데이터를 그대로 전달** — 태그를 다시 대지 않음 |
| 7 | 용량 표시 | 목록 위에 용량 게이지(§2.2 — 분모는 태그 실측 용량), 링크마다 바이트 수치. 링크를 확인할 때 용량도 함께 봄 (**2026-09-30 변경** — 이전에는 「없는 것」이었음) |

**없는 것:** 편집/삭제/순서변경, 기존 레코드 경고(그냥 불러옴).

**예외:** 읽기 전용·NDEF 미포맷 태그 감지 시 ③으로 유도.

### 4.3 ② 수정 · 만들기

**목적.** 태그를 읽고 시작해 편집한 뒤 다시 씀. 태그 접촉 2회. **쓰기가 일어나는 유일한 페이지.**

| # | 요소 | 설명 |
|---|---|---|
| 1 | 용량 게이지 | 게이지 바 + 바이트 수치 병기 (예: `87 / 137 B`). 분모는 태그 실측 용량, 분자는 직렬화 실측 길이 |
| 2 | **AAR 패널** | 링크 행에 붙지 않는 **독립 고정 패널**, 목록 맨 위. "현재 대표 · 서비스명" + 토글 1개. 대표는 항상 목록 1번이므로(아래 4번 "대표 지정" 규칙) 패널이 자연히 대표를 따라감. 초기값 꺼짐, 켜는 순간 고지 시트 노출(§5.4) |
| 3 | 링크 행 | 드래그 핸들(순서 변경) · 대표 지정 버튼 · 삭제. 행 탭 = 기존 링크 수정 |
| 4 | 대표 지정 | 누르면 그 링크가 **목록 맨 위로 자동 이동**. 드래그로는 대표가 안 바뀜 — 명시 선택으로만 |
| 5 | 경고 배지 | 같은 서비스 중복 · 허용 문자 위반 · 형식 이상. **다이얼로그 없이 배지만, 저장 막지 않음** |
| 6 | "링크 추가" 버튼 | 프리셋 선택 화면(§4.4)으로 |
| 7 | "저장" 버튼 | 누르면 **즉시 NFC 대기** — 중간 안내 단계 없음 |

**차단하는 것은 용량 초과 하나뿐.** 중복·형식 오류는 전부 저장 가능(경고만).

**없는 것:** 신규/수정 모드 구분, 태그 잠금 버튼(lock bit 비가역이라 미노출), "대표 없음" 상태.

### 4.4 프리셋 선택 (링크 추가 0단계)

**목적.** 어떤 서비스인지 먼저 고름 — 이 선택이 다음 입력 화면과 정규화 규칙 전체를 가름.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 세로 리스트 | 서비스 이름 + URL 패턴 설명 한 줄. 그리드 아님 — 프리셋 확대를 전제 |
| 2 | 프리셋 6종 | X · GitHub · TikTok · YouTube · Instagram · LinkedIn (글로벌 우선, 국내 서비스 1차 제외) |
| 3 | 기타 1개 | 구분선 아래. 선택지는 1개지만 **저장 개수 무제한** |

**나가는 길:** 프리셋 선택 → 계정명 입력(§4.5) / 기타 선택 → URL 입력(§4.6)

> "저장 완료 후 링크 더 추가하기"(§4.8)를 누르면 홈을 거치지 않고 **여기로 직행**합니다.

**없는 것:** 서비스별 바이트 수치(UI 비노출), 사용자 패턴 직접 등록, "몇 개까지 넣을 수 있음" 안내.

### 4.5 계정명 입력 (프리셋 분기)

**목적.** URL이 아니라 **계정명만** 받음. 완성된 URL은 앱이 조립 — 이 화면이 핵심 UX.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 입력 필드 | 라벨 = "계정명" (URL 아님). 사용자가 `https://`를 칠 일 없음 |
| 2 | 조립 미리보기 | 프리셋 패턴 + 계정명이 실시간으로 완성 URL 표시 |
| 3 | 정규화 표시 | 앞뒤 공백 제거 · 선행 `@` 제거 · 끝 `/` 제거 |
| 4 | 대소문자 | **입력 그대로 보존** |
| 5 | 붙여넣기 감지 | 전체 URL 붙여넣으면 도메인 대조 |
| 6 | 경고 배지 | 허용 문자 위반 · 같은 서비스 중복 (저장은 됨) |

**정규화 순서 (P1~P8)** — §5.1 참고.

### 4.6 URL 입력 (기타 분기)

**목적.** 어떤 URL이든 그대로 받음. 프리셋 분기의 허용 문자 검증은 **여기 적용 안 함**
(적용하면 정상 URL이 전부 걸림).

| # | 요소 | 설명 |
|---|---|---|
| 1 | 입력 필드 | URL 전체 (계정명 아님) |
| 2 | 스킴 자동 부착 | 없으면 `https://` 붙임 |
| 3 | 형식 검증만 | 슬래시·쿼리스트링·포트·경로 전부 허용 |
| 4 | 도메인 추출 | 목록 표시용 라벨 (예: `notion.so`) — 기타가 여러 개면 구분해야 하므로 |
| 5 | 중복 감지 | **URL이 완전히 같을 때만** 경고 (프리셋은 "같은 서비스"가 기준, 여긴 다름) |

**개수 제한 없음** — 유일한 제한은 용량(§2.2 게이지).

### 4.7 NFC 대기 · 검증 재읽기

**목적.** 저장 누르면 곧바로 대기. 쓴 직후 **같은 세션에서 다시 읽어 일치를 확인** —
"저장됨"이라고 말하는 시점이 실제로 검증된 시점이 되도록.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 즉시 대기 | "이제 태그를 대세요" 같은 별도 안내 없음. 저장 버튼 = 대기 시작 |
| 2 | 3단계 진행 표시 | 쓰기 → 검증 재읽기 → 완료 |
| 3 | "떼지 마세요" 문구 | 2단계 존재가 사용자에게는 예상 밖이므로 명시 |
| 4 | 태그 인식 대기 타임아웃 | Android는 요청 시작 후 30초. iOS는 시스템 세션 종료를 처리. 시간 초과 시 자동 재시작 없이 **"다시 시도" 버튼** |

**나가는 길:** 검증 일치 → 완료(§4.8) / 불일치 → 쓰기 실패(§4.9, 부분 기록 가능성 때문에
재시도 아닌 **전체 재쓰기**) / 타임아웃 → 같은 화면에서 재시도.

**구현 확인 필요:** `reconnectAfterWrite` 옵션이 이 검증 재읽기에 쓰일 수 있는지, iOS 타임아웃 실제 시간.

**2026-10-11 구현·실기기 확인 대기:** Android 제한은 링크 읽기·편집 진입 읽기·태그 진단·저장의 태그 인식 대기에 공통 적용한다. 이전 NFC 정리를 기다린 뒤 새 인식 요청부터 시간을 재며, 태그 연결 직후 타이머를 해제하여 실제 읽기·쓰기·검증은 대기 타이머로 중단하지 않는다. 시간 초과 시 세션 정리를 완료하고 사용자가 누를 때만 새 요청을 연다. 저장 대기 실패 시 링크·비URL·기존 AAR의 전체 스냅샷을 유지한다. iOS의 실제 종료 시간은 미측정이며 AAR 쓰기 범위는 확대하지 않는다.

### 4.8 완료

**목적.** 저장 성공 후 곧장 홈으로 튕기지 않고 사용자가 다음 행동을 고름.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 성공 표시 | 검증 재읽기 통과 후에만 표시 |
| 2 | 요약 | 저장된 링크 개수 + 최종 사용량 |
| 2a | AAR 안내 | 대표에 AAR을 켜서 저장했을 때만 1줄 (예: "안드로이드에서 인스타그램 앱으로 바로 열립니다") |
| 3 | "완료" 버튼 | 홈으로 |
| 4 | "링크 더 추가하기" 버튼 | **프리셋 선택 화면으로 직행**(홈 안 거침) — **같은 태그**에 이어서 추가 |

**두 번째 갈래("링크 더 추가하기")에서 이어지는 것:** 태그 용량(재읽기 없이 실측값 유지) ·
현재 링크 목록 · 용량 게이지(계속 갱신) · 대표 링크(기존 유지, 바꿀 수 있음) · AAR 고지는
**이 세션 첫 1회만**(수동으로 다시 켜면 재노출).

> 저장은 매번 탭이 필요합니다 — 링크 추가 후 다시 저장 누르면 태그를 한 번 더 대야 함.

### 4.9 쓰기 실패

**목적.** 검증 재읽기 불일치 감지 시. 부분 기록 가능성 때문에 **재시도가 아니라 전체 재쓰기**로.

| # | 요소 | 설명 |
|---|---|---|
| 1 | 감지 | U3 검증 재읽기 불일치 (쓰기 API가 성공을 반환해도 여기서 걸림) |
| 2 | 안내 | "실패"가 아니라 **"부분 기록 가능성"**으로 표현 |
| 3 | 편집 내용 보존 | 구성한 링크 세트는 화면에 그대로 남음 (재입력 불필요) |
| 4 | 주 동작 | **전체 재쓰기.** "부분 재시도"/"이어서 쓰기" 없음 |
| 5 | 보조 동선 | ③ 태그 상태 확인 (태그 자체 문제인지 가려냄) |

**없는 것:** 자동 재시도, 오류 코드 노출.

### 4.10 ③ 태그 상태 확인

**목적.** 태그 자체를 **진단만**. 태그 접촉 1회, 쓰기 버튼 없음, 나가는 길은 홈뿐인 막다른 페이지.

| # | 요소 | 출처 |
|---|---|---|
| 1 | 전체 용량/사용량/남은 용량 | `getNdefStatus().capacity` + 현재 메시지 직렬화 길이 |
| 2 | 쓰기 가능 여부 | `getNdefStatus().status` |
| 3 | NDEF 포맷 여부 | `status === NotSupported` |
| 4 | 기록된 레코드 개수 | 읽은 NDEF 메시지 |
| 5 | AAR 상태 | 읽은 메시지에 AAR이 있는지, 어떤 서비스인지. 없으면 이 줄 자체가 없음 |

전부 **한 번의 조회**에서 나오므로 별도 구현이 거의 없습니다.

**상태 3가지를 전부 정의해야 함:**

| `NdefStatus` | 화면 | ②에서 할 수 있는 것 |
|---|---|---|
| `ReadWrite` (2) | 정상 — 용량 게이지 | 전부 가능 |
| `ReadOnly` (3) | "이 태그는 잠겨 있습니다" | 조회만, 저장 차단 |
| `NotSupported` (1) | "NDEF 태그가 아닙니다" | 포맷 유도 또는 사용 불가 안내 |

**없는 것:** 잠금 실행 버튼(lock bit는 static·dynamic 둘 다 OTP — 비가역이라 노출 안 함),
수정 버튼(③→②로 가는 버튼 없음, §3 참고).

## 5. 핵심 로직 스펙

### 5.1 입력 정규화 파이프라인 — 선택이 먼저, 그다음 두 갈래

```
0단계: 프리셋 도메인 / 기타 선택   ← 이 선택이 이후 전부를 가른다
        │
        ├─ 프리셋 분기 (입력 = 계정명)          ├─ 기타 분기 (입력 = URL 전체)
        │   P1. 앞뒤 공백 제거                   │   E1. 앞뒤 공백 제거
        │   P2. 전체 URL 붙여넣기 감지            │   E2. 스킴 없으면 https:// 부착
        │       → 도메인 일치 시 계정명만 추출     │   E3. URL 형식 검증만 (슬래시/쿼리/포트/경로 전부 허용)
        │       → 다르면 "기타로 추가?" 제안       │   E3a. 추적 파라미터 제거 (utm_source·utm_medium·utm_campaign·igsh)
        │   P3. 선행 @ 제거                       │   E4. 도메인 추출 → 목록 표시 라벨
        │       (유튜브·틱톡은 저장 시 재부착)      │   E5. 중복 감지 — URL 완전 일치 시만 경고
        │   P4. 끝의 / 제거                       │
        │   P5. 허용 문자 검증 (영숫자 . _ - 만)   │   ※ P5는 여기 적용 안 함 — 정상 URL이 걸림
        │   P6. 대소문자 그대로 보존               │   ※ P7(조립) 없음 — 입력이 곧 저장 URL
        │   P7. URL 조립 = 프리셋 패턴 + 계정명    │
        │       예) Instagram+"hong"              │
        │        → https://www.instagram.com/hong/│
        │   P8. 중복 감지 — 같은 서비스면 경고     │
        ▼                                        ▼
              목록에 추가 → 용량 게이지 갱신 (여기서부터 다시 하나)
```

> **왜 분리되어야 하는가:** P5(허용 문자 검증)를 공통 단계로 두면 기타 분기의 정상적인
> URL(슬래시, 콜론 포함)이 전부 걸립니다. "기타는 어떤 URL이든 넣을 수 있다"가 성립하려면
> 두 파이프라인이 완전히 분리돼 있어야 합니다.

> **E3a 주의 (2026-09-20 결정 — 현행 유지).** 현재 구현(`urlNormalizer.ts:32-49`)은 파라미터를
> 지울 때 **쿼리 전체를 다시 씁니다.** 꼬리표가 있고 동시에 URL에 `~` · 공백 · 값 없는 키가
> 들어 있으면 저장된 URL이 입력과 달라집니다 — **기타 링크가 저장 후 안 열리면 여기부터 보세요.**
> 문제가 확인되면 URL 파서를 거치지 않고 해당 키만 잘라내는 방식으로 교체합니다.

**모든 검사는 경고 배지이고 저장을 막지 않습니다.** 앱이 물리적으로 막을 수 있는 건
**용량 초과뿐**입니다. 계정 실존 여부는 서버가 없어 검증 불가(형식 검증까지가 전부).

### 5.2 프리셋 목록과 URL 패턴

| 서비스 | 저장 URL 패턴 | 계정명 허용 문자 |
|---|---|---|
| X | `https://x.com/{handle}` | 영숫자 `.` `_` `-` |
| GitHub | `https://github.com/{handle}` | 영숫자 `.` `_` `-` |
| TikTok | `https://www.tiktok.com/@{handle}` | 영숫자 `.` `_` `-` |
| YouTube | `https://youtube.com/@{handle}` | 영숫자 `.` `_` `-` (3~30자, YouTube 공식 규칙과 정확히 일치) |
| Instagram | `https://www.instagram.com/{handle}/` | 영숫자 `.` `_` `-` |
| LinkedIn | `https://linkedin.com/in/{handle}` | 영숫자 `.` `_` `-` |
| 기타 | 사용자 입력 그대로 (+ 스킴 자동 부착) | 제한 없음 |

> Instagram·TikTok은 `www.` + (Instagram은 끝 슬래시) 포함이 실제 표준 표기입니다 —
> 자동완성 조립 시 이 표기를 따르세요.

### 5.3 편집 화면 진입 규칙

`②` 진입 시 **항상 먼저 태그를 읽습니다.** 신규/수정 모드 구분 없음 — 빈 태그면 목록이
비어있을 뿐. `①`에서 "수정하기"로 들어온 경우엔 이미 읽은 데이터를 그대로 사용, 재읽기 없음.
"링크 더 추가하기"(§4.8)로 돌아온 경우도 방금 쓴 상태를 그대로 이어감 — 재읽기 없음.

### 5.4 AAR 고지 시트

AAR 토글을 켜는 순간(꺼진 상태 → 켜는 동작에서만) 고지 시트가 뜹니다. 기본 포커스는
"켜지 않음". 문구 핵심: **"앱이 없으면 링크 대신 앱 설치 화면이 열립니다."**
같은 세션에서 "링크 더 추가하기"로 연속 저장하며 계속 켜진 채로 저장하면 **최초 1회만**
고지하고, 사용자가 수동으로 껐다 다시 켜면 다시 고지합니다.

### 5.5 저장 시 직렬화 순서

```
[0] 대표 링크 URI 레코드           ← 첫 레코드 (필수 — iOS/Android 둘 다 첫 레코드만 해석)
[1..n] 나머지 URI 레코드 (표시 순서대로)
[last] AAR 레코드 (켜져 있을 때만) ← 반드시 마지막 (첫 레코드면 안 됨)
```

저장 버튼을 누르면 이 순서로 빌드한 NDEF 메시지 전체를 **한 번에** `writeNdefMessage`로 씁니다.
매번 "기존 레코드 + 새 레코드"가 아니라 **매번 처음부터 전체 재작성**입니다 (부분 갱신 없음).

### 5.6 용량 초과만 저장을 막음

| 상황 | 처리 |
|---|---|
| 같은 서비스 중복 | 경고 배지, 저장 가능 |
| 커스텀 URL 완전 중복 | 경고 배지, 저장 가능 |
| 형식 오류 | 경고 배지, 저장 가능 |
| **용량 초과** | **저장 차단** — 무엇을 빼야 하는지 표시 |

### 5.7 쓰기 → 검증 재읽기 → 완료/실패

```
저장 버튼 누름
  → NFC 대기 시작 (§4.7)
  → 태그 감지 → writeNdefMessage(전체 메시지)
  → 같은 세션에서 즉시 다시 읽기 (getNdefMessage)
  → 방금 쓴 내용과 바이트 단위로 대조
       일치   → 완료 화면 (§4.8)
       불일치 → 쓰기 실패 화면 (§4.9) → "전체 재쓰기"로만 복구, 부분 재시도 없음
```

## 6. 만들지 말아야 할 것 (범위 밖 — 명시적으로 뺀 것들)

- 로그인/계정, 서버 API 호출, 로컬 DB/캐시(AsyncStorage 포함) — **앱은 아무것도 저장하지 않음**
- "1탭 모드"(캐시 우선 읽기) — 편집은 항상 태그를 읽고 시작하므로 성립하지 않음
- 태그 잠금(lock bit) 실행 UI — 비가역이라 노출하지 않기로 결정
- 태그 복제, 여러 태그 일괄 관리 — 태그 UID 식별 자체가 1차 범위 밖
- `NDEF_DISCOVERED` 인텐트 필터 등록 — **절대 등록 금지.** 등록하면 앱 없이 탭했을 때 링크
  대신 우리 앱이 뜨게 되어 명함처럼 쓰는 핵심 시나리오가 깨짐
- AAR을 여러 개 저장, 프리셋과 무관하게 임의 패키지명 지정 — 태그당 최대 1개, 대표와 동기화만

## 7.1 현재 코드에서 발견된 수정 항목 (ver2에서 처리)

데모 코드 검토(2026-09-20)에서 나온 것. **4개 중 3개는 기획 문서 4종(HANDOFF · DECISIONS ·
VERIFICATION · SPEC-T6-AAR) 어디에도 없는 내용**이라, 스펙을 충실히 따라 만들어도 그대로
재발한다. 스파이크(§9-1) 때 같이 처리할 것.

전부 `src/nfc/nfcService.ts` 한 파일 안에 있다.

| # | 증상 | 위치 | 스펙에 있나 |
|---|---|---|---|
| 1 | 읽기전용 태그 저장 시 "읽기 전용입니다" 대신 "태그를 찾지 못했습니다"가 뜸 | `nfcService.ts:178,187` | ❌ 없음 |
| 2 | 증상 없음 (겉보기 정상) | `nfcService.ts:199-200` | ✅ §5.7 |
| 3 | 같은 링크 2개 저장 시 "일부만 기록되었을 수 있습니다" (실제로는 정상 저장) | `nfcService.ts:123,200` | ❌ 없음 |
| 4 | 깨진 태그를 읽으면 `https://null`이 정상 링크처럼 목록에 뜸 | `nfcService.ts:130` | ❌ 없음 |

### 처리 방법 — 수정 3개로 4개가 닫힌다

**A. 검증을 바이트 비교로** → 2번 + 3번 해결
현재는 읽어온 메시지를 `extractUrls`로 문자열 변환 후 비교한다. 그 변환에 중복 제거가
들어 있어 3번이 발생. 쓸 때 만든 `bytes`(`:183`)와 읽어온 바이트를 직접 대조하면
`extractUrls`가 검증 경로에서 빠지므로 둘 다 사라지고, §5.7 "바이트 단위 대조"에도 맞는다.

**B. 읽은 URL을 목록에 넣기 전 검증** → 4번 해결 + 보안 항목 1건
`push()`(`:121-124`)가 현재 빈 문자열만 거른다. http/https 검증을 추가.
`utils/urlNormalizer.ts`의 `isValidHttpUrl`을 그대로 쓰면 된다.
→ 태그에서 읽은 문자열이 검증 없이 `Linking.openURL`로 가던 문제도 같이 막힌다.

**C. 상태 조회 실패 시 동작 정의** → 1번 해결
`getNdefStatus()`가 `.catch(() => null)`(`:177`)로 떨어지면 `if (status)`와
`status?.capacity &&`가 모두 거짓이 되어 **읽기전용·NDEF·용량 검사 3개가 통째로 스킵**된다.
**결정(2026-09-20): 중단.** 태그는 인식됐으나 **상태를 확인할 수 없으면 쓰지 않고 멈추고
다시 대게 한다.** 읽기(`:228`)·저장 직전(`:177`) **두 곳 모두** 적용 — ②는 태그를 2번 대므로
저장 시점의 조회는 독립된 사건이다. 재시도는 자동이 아니라 사용자가 다시 대는 방식(§4.7-4 · U9).

### 재현 방법

| # | 재현 |
|---|---|
| 1 | 읽기전용 태그에 저장 → 에러 문구 확인 |
| 2 | 일상 조작으로는 재현 불가 — 코드 검토로만 확인되는 항목 |
| 3 | 같은 URL 2개 추가 → 저장 → 실패 문구가 뜨면 재현 |
| 4 | 비정상 UTF-8 바이트가 든 URI 레코드 태그 읽기 → 목록에 `https://null` |

### 참고 — 용량 상수 137 vs 144

위 4건과 별개. **기능을 만들면 해소되지만 숫자는 기록해둔다.**

**2026-10-09 현재:** 4단계에서 144 B 상수를 제거하고 `getNdefStatus().capacity` 실측값을 분모로 연결함.
NTAG213의 사용자 메모리는 144 B이며 Android 실측 NDEF capacity는 137 B(2026-10-02).

AAR을 켜도 **분모는 태그 실측 용량 그대로**다. AAR은 전체 직렬화 사용량(분자)에만 들어가고 링크에 쓸 수 있는 여유가 줄어든다.
Instagram AAR 실제 추가분은 39 B이므로 capacity 137 B인 태그에서 링크에 쓸 수 있는 여유는 최대 98 B.
프리셋별 AAR 추가분은 실제 `Ndef.encodeMessage`로 계산하며 40 B 추산이나 137 B 상수를 구현에 사용하지 않는다 (§2.2, `SPEC-T6-AAR.md §5.3` 정정).

## 9. 권장 구현 순서

1. **스파이크** — 빈 태그에 URL 하나 쓰고 다시 읽기 (§1의 3개 실측값 확보)
   → **§7.1의 수정 A·B·C를 이 단계에서 같이 처리** (같은 파일, 같은 코드 블록)
2. **읽기 경로** — 홈 → ① 읽기 (가장 단순한 화면, NDEF 파싱/대표 판별 로직의 기반)
3. **쓰기 경로** — ② 편집(대표 지정 없이 단순 추가/삭제) → 프리셋/기타 입력(§5.1) →
   저장 → NFC 대기/검증 재읽기(§5.7) → 완료/실패
4. **용량 게이지** (§2.2, §5.6) — ②에 실시간 반영
5. **③ 태그 상태 확인** — ①·②와 같은 API를 재사용하므로 마지막에 붙여도 무방
6. **AAR 옵션** (§2.3, §5.4, §5.5) — 나머지가 안정된 뒤 추가. 초기값이 전부 꺼짐이라
   기능 자체를 안 켜도 기존 플로우에 영향 없음
